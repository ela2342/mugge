## F-314: Hot venue switch with gate open applies new gains instantly, without confirmation

**Severity:** CRITICAL (speaker damage risk; audio-engineer)
**Status:** open — escalated to owner by audio-engineer via team-lead (2026-10-24). Exists on main since US-113 (PR #22).
**Found in:** `src/graph-manager/src/main.rs:742-760` (`set_venue`), `src/web-ui/static/js/venue.js:176-207`, `src/web-ui/app/venue_routes.py:113`
**Affects:** D-063 (universal audio gate), D-009, D-031, US-113, US-146
**Related:** F-271 (no D-031 protection WAVs, dirac on ch 1-4), F-315, F-298, F-320, F-037; **fix story:** US-159
**Found by:** audio-engineer (safety.md D-063 review, 2026-10-24)

### Description

`set_venue` hot-applies the new venue gains in a single step while the gate
is open: no ramp, no confirmation. The UI's venue Apply has no confirmation
dialog and is not disabled while the gate is open. Example: switching from
production to foh-passthrough is a +60/+64 dB jump into 4x450 W, with dirac
coefficients on ch 1-4 (no crossover or subsonic protection, F-271).

### Interim operator rule (until fixed)

Never change venue with the gate open. Close the gate, apply, verify,
re-open. Documented in safety.md by technical-writer.

### Fix condition (audio-engineer)

Enforced in GraphManager, not only in the UI. With the gate open,
`set_venue` either returns an error, or closes the gate and requires a
confirmed re-open. The architect picks the mechanism.

**Architect ruling (2026-10-24), agreed with AE and UX:** a single gate
module in GM owns all Mult writes; `set_venue` with the gate not Closed
returns an error and mutates nothing; venue coefficients are checked by
content hash; the UI offers "CLOSE GATE & LOAD VENUE" and never re-opens
automatically. Full requirements in US-159 (G1-G10, U1-U5, T1-T8).

### Veto

Audio-engineer veto applies to any PR touching gate, venue or first-boot
logic until this is fixed. It lifts when US-159 lands with real-stack Mult
tests (US-159 T1-T6) and AE has reviewed the diff.
