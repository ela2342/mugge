## F-410: Unmute restores the venue gains behind a closed gate

**Severity:** HIGH (audio-engineer, ruling `adf62efa`, 2026-10-27, on the CI evidence below; was P2 since backlog v266). Audio-engineer, verbatim: "It is a pre-audio gate. It must be fixed before the first gate open with amps connected, alongside F-341 (7f73dda1) and F-465 (013d2fa8)."
**Status:** open. Hard pre-amps gate (amps-on precondition row 20 in `docs/operations/safety.md`, with F-320 D; no interim operating rule counts). Folded into the F-439 PR (PO placement `123cb139`); closes with that PR after AE acceptance. No action while "nothing connected" stands
**Owner:** worker-3, in the F-439 PR (PO `123cb139`; this supersedes the earlier worker-1 assignment)
**Found in:** `src/web-ui/app/audio_mute.py` (`AudioMuteManager.unmute()`, l.102-134 at `ff55d0c8`), first by reading the code at F-394 head `e050fe90`. Then seen in CI: PR #66 S2-6, run 40501858451 (head `6931c372`), log `c446e8cb`

### Description

`AudioMuteManager.unmute()` writes the stored pre-mute Mult values back
to the gain nodes without checking the gate. Worker-1, verbatim: "So
mute → gate close → unmute puts the venue gains back on while the GM
reports gate_open=false. That is a gain increase behind a closed gate."

The GM's gate is the gains themselves: `CloseGate` sets every Mult to
0 (`src/graph-manager/src/main.rs` l.824-835 at `ff55d0c8`), and the
Standby transition closes the gate the same way (l.575-583).
Audio-engineer, verbatim: "So unmute() after a close turns the output
fully back on at venue gain while the GM reports gate_open=false.
Unlike OpenGate's 30-step ramp [in effect also a single step, F-315], it jumps the gain in a single step, and
it also undoes automatic closes (Standby, main.rs:575-582)."

### CI evidence (PR #66 S2-6)

In run 40501858451 the `virtual_gate_open` fixture read hw-out ch 1-4
before it opened the gate, with the -20 dBFS tone on level-bridge-sw,
and got `[-40.0, -40.0, -34.0, -34.0]`. Audio-engineer, verbatim:
"These are exactly the open-gate venue levels ... The path really was
passing audio at venue gain while the GM reported the gate closed."

Sequence in the stack log (l.8062-8136 of `c446e8cb`):

- 12:38:55.519 GM "D-063: Gate closed on standby transition"
- 12:38:55.593 web UI "Muted all 8 gain nodes"
- 12:38:55.678 web UI "Unmuted all gain nodes"
- then standby → dj, and the fixture reads venue levels on hw-out.

The audio-engineer rules it a product defect exposed by CI, not a
flake: "I do not accept a green rerun as evidence that the issue is
gone." PR #66 did not cause it (its diff touches no mute, gate, GM or
pw_helpers code). The two mute tests are correct and must not be
xfailed or skipped.

### Fix requirements (audio-engineer, `adf62efa`, verbatim)

- F1. Unmute must never write a non-zero Mult while the GM gate is
  closed. If the gate is closed, unmute clears the mute state and the
  snapshot, leaves the Mults at 0, and reports it.
- F2. Any gate close (standby, close_gate, watchdog, D-063) must
  invalidate the web-ui pre-mute snapshot. Better: the GM owns mute, so
  that only one process writes Mults. The Architect picks the shape.
- F3. The mute snapshot must come from a confirmed live read, not a
  pw-dump that may be stale (same rule as F-439 C2/C5).

### Placement and acceptance (PO `123cb139`, AE release `3088f33b`)

F-410 is folded into the F-439 PR (owner worker-3). The PR order stays
#63 → F-465 → F-341 → F-439 → #66. F-439 scope r3 (`67f15d65`) makes
MUTE = close_gate and removes unmute as a gain restore, so F1-F3 hold
by construction. Conditions for the F-439 PR:

1. The PR body maps AE F1-F3 one by one to how r3 removes each one,
   and cites `adf62efa`.
2. AE tests, adapted to r3:
   (a) open gate → mute → close_gate → all 8 Mults == 0 and hw-out at
   the floor; no web UI action other than Open Gate raises any Mult.
   (b) standby transition immediately followed by mute (the CI order)
   → all 8 Mults == 0; this also shows whether the GM's own zeroing
   lands.
   (c) the `test_mute_e2e` fixtures stay unchanged and pass. None is
   xfailed or skipped. `test_unmute_restores_levels` may be rewritten
   with the QE, never xfailed, skipped or deleted; it must assert that
   after the old "unmute" call (or its 404/410) all 8 Mults are still 0
   and hw-out is at the floor (AE NB1).
3. If test (b) shows that the GM's own standby/close zeroing does not
   land, the QE/AE file that as a separate GM defect at once.
4. F-410 closes with the F-439 PR, after AE acceptance.

AE NB2: the GM watchdog unlatch still writes a hardcoded Mult table.
That is the same class of defect on the GM side, owned by F-320 D. The
F-439 PR body names F-320 D as its owner, and the AE acceptance of
F-320 D re-checks F1 on the GM side.
