## F-363: Purifi Qts test is order-dependent and hides a data error

**Severity:** medium (quality-engineer)
**Status:** resolved. PR #56 merged 2026-10-25 (`1c36889f`). All 3 acceptance criteria met (see Resolution)
**Found in:** `src/room-correction/tests/test_driver_validation.py:610`, `TestRealDriverRecords::test_sample_real_drivers_pass` (`iterdir()[:20]`); data in `configs/drivers/purifi-ptt6-5w04-nfa-01/driver.yml` (from `36386c75`)
**Affects:** T1 on any platform whose directory order puts the Purifi record in the first 20
**Related:** US-163 (PR #50 CI)
**Found by:** worker-2; re-found by worker-1 (2026-10-25)

### Description

The test checks a sample of driver records taken as the first 20
entries of an unsorted `iterdir()`, so which records it checks
depends on filesystem order. On darwin the sample includes
`purifi-ptt6-5w04-nfa-01`, and the test fails on main (`95306f66`)
and on the US-163 branch. Linux CI may pass by order alone.

The record lists Qts 0.23, but its Qes 0.27 and Qms 6.3 give
Qts 0.2589, an 11.2% mismatch against the 10% limit. So there are
two faults: a latent data error and an order-dependent test.

### Acceptance criteria

1. Qts (and Qes/Qms) for the Purifi record verified against the
   manufacturer's datasheet and corrected.
2. The test checks all records, or a sorted, deterministic sample.
3. The test passes on Linux and darwin.

### Resolution (2026-10-25, PR #56, merge `1c36889f`)

1. AC1: the Purifi record is corrected from the manufacturer data
   sheet (rev 0.91): Qts 0.23 -> 0.26 (`4afb8235`). The same commit
   changes 28 more records (corrections from their cited data sheets,
   or exemption marks), each with an `F-363:` note giving source,
   revision and retrieval date.
2. AC2: `test_sample_real_drivers_pass` (first 20 of an unsorted
   `iterdir()`) is deleted. `test_all_real_drivers_pass` validates
   all 2345 driver records (`f4d92a6e`).
3. AC3: the suite no longer depends on directory order, so Linux and
   darwin check the same records. darwin: 1210 passed / 1 skipped at
   the final head `684da11a`; Linux: CI T1 green at the merge (Linux
   CI 40236821737: 1210 passed / 1 skipped).

Also in PR #56:

- **Exemption table.** Records whose data sheet itself prints an
  inconsistent Qts/Qes/Qms triple, or whose triple fails the check
  and whose source is unavailable, carry
  `ts_consistency: datasheet-inconsistent` or `unverifiable` and a
  matching `TS_CONSISTENCY_EXEMPTIONS` entry in
  `test_driver_validation.py` (the exemption table has 8 records).
  Tests keep the marks and the table in step, check that each entry
  still matches its record, and check that no speaker or venue config
  references a marked record. `configs/drivers/TEMPLATE.yml` documents
  the field.
- **Plausibility bounds** (`e9a96c60`): Qts 0.1-5.0, Qes 0.1-10.0,
  Qms 0.5-50.0, with an allowlist for checked exceptions. They catch
  comma-decimal scrape errors that still pass the 10% consistency
  check (e.g. Qms 654.0 for 6.54). An allowlisted value with no source
  must carry ts_consistency: unverifiable (3 records:
  factory-buyouts-42-41716g-001, tang-band-w1-2361s, visaton-g-50-ffl),
  so 11 records carry a mark in total; test_exemptions_match_marks
  checks the marks against both tables.
