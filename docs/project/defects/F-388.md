## F-388: Xmax definition unknown in the excursion-mask derivation

**Severity:** P2 (audio-engineer)
**Status:** open. ACs accepted by the AE (2026-10-25). Precondition for F-385 option (i') (CHN-50P excursion mask)
**Found in:** D-031 / excursion-mask derivation; `xmax_mm` and `ts_consistency` in `configs/drivers/*/driver.yml`
**Affects:** any safety computation that reads driver records (excursion mask, thermal, protection, D-031 derivation)
**Related:** F-363 (PR #56), F-385, D-031
**Found by:** audio-engineer, from the F-363 record corrections; ACs from the #56 Rule 13 reviews (advocatus-diaboli, quality-engineer, architect)

### Description

Driver records store `xmax_mm` without saying which Xmax definition it
is. Manufacturers print different things under the same name: a
measured linear limit (e.g. Klippel), the plain overhang
((winding depth - gap depth)/2), or a "mathematical" Xmax that adds
terms such as + gap depth/4. Only the first two are usable as a
linear excursion limit.

Trigger: F-363 corrected PRV 10MR2000-NDY `xmax_mm` 5.0 -> 7.15 to
the data sheet's printed "Excursion (mathematical) Xmax". Using
7.15 mm as a linear limit is less conservative than the plain
overhang, which re-derives to (18.8 - 9.0)/2 = 4.9 mm. The 2345
scraped records likely carry the same unknown definition.

Second fault: no code reads the `ts_consistency` marks added in
F-363. `speaker_sim.load_driver` loads marked records like any other.
Today the only guard is the F-363 test that no config under
`configs/` references a marked record.

### Acceptance criteria

1. M1 (AE): "Every safety computation that reads a driver record
   (excursion mask, thermal, protection, D-031 derivation) refuses at
   load any record that has a ts_consistency mark, or has a null in a
   field the computation needs. The error names the record, the mark
   or the field, and the computation. It fails closed: no fallback
   values, no skipping the channel. Simulation (speaker_sim) may
   still load marked records, but it logs the mark, and its output
   must never feed a safety gate."
2. M2 (AE): "Driver records get xmax_definition with values linear
   (manufacturer measured linear limit, e.g. Klippel), overhang
   (plain (winding depth - gap depth)/2), mathematical (overhang plus
   terms such as + gap depth/4), or unknown. Safety computations use
   linear and overhang as stored. A mathematical Xmax is re-derived
   as the plain overhang from the datasheet's winding and gap depths,
   and both figures are recorded; if the depths aren't printed, it is
   rejected. An unknown Xmax is rejected. No percentage derate
   factors. Only the drivers referenced by speaker identities need a
   classification (AE), starting with markaudio-chn-50p (xmax 3.5)
   before the F-385 mask. The 2345 scraped records may stay unknown."
3. AC-b (QE, architect): correct the "keeps it out of the safety
   math" comment in `test_driver_validation.py`.
4. AC-c (QE): a paired loader test. A record marked `unverifiable`
   is refused AND a normal record is still accepted in the same test,
   so the positive control proves the loader doesn't refuse
   everything.
5. AC-e (QE): a test for the Xmax handling once a consumer of
   `xmax_mm` exists.
