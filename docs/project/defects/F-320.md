## F-320: D-063 gate state is not authoritative — gate can read CLOSED while audio is live

**Severity:** high (audio-engineer). Becomes a remote path when combined with F-037 (see F-037).
**Status:** open — D fixed 2026-10-27 (F-320 D, branch `fix/F-320D-unlatch-no-mult`); E, F and G open. Routed to architect for design. Sub-item E needs an owner decision. All three found in code (technical-writer) and verified by AE through code reading. None of them has been tested on the Pi yet; E is unverified at runtime.
**Found in:** `src/graph-manager/src/main.rs:660-699`, `:251-253`; `src/graph-manager/src/registry.rs:520-529`; `nix/nixos/services/graph-manager.nix` (Restart=on-failure, RestartSec 3); `src/web-ui/app/audio_mute.py` (l.102-140)
**Affects:** D-063, US-113, US-123, US-126, US-144, US-150, US-151
**Related:** F-037, F-298, F-314, F-315, F-332 (same module as F), F-344 (same bypass via the Config tab gain Apply), F-345 (thermal limiter); **fix story:** US-159
**Found by:** technical-writer (safety.md D-063 drift check), verified by audio-engineer (2026-10-24)

**See also:** F-338 (UI CLOSE GATE disabled while CLOSED), F-339 (CloseGate false success).

### Description

Three paths leave the gate showing CLOSED while gains are above zero (D-F), plus a spec gap (G):

- **D — watchdog unlatch** (`main.rs:660-699`). The pre-mute gains come back
  instantly, with no ramp, and `gate_open` stays false.
  Amended 2026-10-24 (architect B, AE High): the restored gains are a
  hardcoded table (`main.rs:661-695`, `registry.rs:484-496`), not the
  pre-mute values: -60 dB (0.001) on mains, HP and IEM, -64 dB
  (0.000631) on subs, written with no gate check even when the gate
  was Closed before the latch; the UI keeps showing CLOSED. On
  `markaudio-ultimax-200hz` a spare output goes from -120 to -64 dB
  (+56 dB). The level alone is not damaging; the danger is that a
  non-zero Mult turns off the hard-zero path, so a NaN latched in a
  convolver comes out (F-349). Reachable over the localhost RPC only,
  hence High, not Critical (AE).
  `registry.rs:520-529` closes the gate on watchdog mute, and its comment
  says the operator must re-open it, but unlatch skips that step.
  Fixed 2026-10-27 (F-320 D, branch `fix/F-320D-unlatch-no-mult`): the
  gain table and the pre-mute store are deleted. `watchdog_unlatch` only
  clears the latch (`watchdog::handle_unlatch` gets no graph or registry
  handle, so it cannot write a Mult). `open_gate` is refused while
  latched, before any other check, with an error starting "watchdog
  latched: gate stays closed, no gain changed". The `watchdog_unlatched`
  event has no gain count and `watchdog_status` has no `pre_mute_gains`.
- **E — GM restarts while PipeWire keeps running** (unverified at runtime).
  On startup GM sets `gate_open=false` (`main.rs:251-253`), but it never
  reads or writes Mult. With Restart=on-failure (RestartSec 3), a crash or
  redeploy while the gate is open leaves audio running at venue gains
  while GM reports CLOSED.
- **F — web UI MUTE/UNMUTE bypasses the gate** (`audio_mute.py`). MUTE sets
  the Mults to zero via pw-cli and keeps the old values in memory, but GM
  is never told. UNMUTE (l.102-140) puts those values back with no ramp and
  no gate check, even after a venue change or a `close_gate`. It also goes
  wrong the other way: `open_gate` or a venue hot-switch brings the gains
  back while the UI still shows MUTED.
- **G — D-063 `audio_enabled` not implemented** (technical-writer). D-063
  specifies an `audio_enabled` field in `active.yml`, reset on every boot.
  Nothing in `src/graph-manager/src` or `src/web-ui/app` implements it; the
  gate is purely in-memory GM state, which is the root of E.

### Fix direction

- D: unlatch only clears the latch. Gains stay at 0 and the gate stays
  closed. Recovery goes through `open_gate`, with confirmation and ramp.
- E: **owner decision.** Either zero the gains on start (safe, but a crash
  silences the show), or adopt the existing state: read back the Mults,
  report OPEN if any is above 0, and warn (O-12).
  AE position (2026-10-24, corrects the earlier "adopt" recommendation): under either option the gate never reads CLOSED while any Mult is above 0. AE recommends zero on start (simpler, fully verifiable; matches US-159 G5/T5). Adopt is an acceptable owner option for show continuity only if the adopted values pass G3 validation (finite, at most 1.0, at most the per-speaker ceiling) and the graph passes the G4 health check; otherwise GM falls back to zero. If the owner chooses adopt, T5 asserts the invariant plus that validation.
- F: GM is the single source of truth. MUTE = `close_gate`. UNMUTE is
  either removed or becomes `open_gate` with confirmation and ramp.
- **Hard invariant, whichever option is chosen:** the gate never reports
  CLOSED while any Mult is above 0.

### Acceptance test (link to F-298)

After each of the paths D, E and F, a pw-dump-based check asserts
`gate_open == (any Mult > 0)`.

### Interim operator rules (safety.md, technical-writer)

- Rule 5: after a watchdog unlatch or any GM restart, treat every output
  as live. Press Close Gate before assuming silence.
- Rule 6: never use UNMUTE. To recover from MUTE, press Close Gate, then
  Open Gate.

### Design ruling (architect + AE + UX, 2026-10-24)

Fixed by US-159 (GM gate module, sole owner of all Mult writes). D: G6
(unlatch clears the latch only, refuses while the cause persists). E: G5/G5a
(active zero write and read-back on start), which differs from the "adopt
state" option AE recommended earlier, so O-12 stays open for the owner.
F: U5. G: US-159 G10. The invariant test is US-159 T8.
