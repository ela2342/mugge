**Severity:** HIGH (architect, ruling `827c2d69` §3, 2026-10-27: "priority HIGH, because the DJ path needs a venue"). Audio-engineer (`013d2fa8` (B)1): a HARD PRE-AUDIO GATE.
**Status:** fix merged (PR #72, head `69004e63`, merged to main as `d12661e3`, 2026-10-28). Still open: deploy to the Pi 5 and on-device AC3 (b-e) on that generation, parked while the owner is travelling (no Pi access). The F-465 rule and amps-on row 19 in `docs/operations/safety.md` stay in force until then
**Owner:** worker-1 (fix and deploy plan); architect rules, audio-engineer releases
**Found in:** no nix file set `PI4AUDIO_VENUES_DIR` (origin/main and #63 head `3f28b6c7`). **Affects:** venue arming (`set_venue`, `get_venue`), gate open, every DJ session on the Pi 5
**Related:** F-467 (fixed inside the same PR as its own commit), F-341 (see the close-out note below), F-466 (process lesson from the same finding), F-472 and F-037 (restore of an armed venue), F-487 (the select path of the same class: #72 makes every packaged venue selectable on the Pi, including `foh-passthrough` and `local-demo`, which have no D-031 driver protection), US-113, US-123, D-062, `docs/operations/safety.md` row 19
**Found by:** architect, during the #63 S1 session (step P9, ruling `827c2d69`)

### Description

The GM looks for venue files in `PI4AUDIO_VENUES_DIR`, or in
`./configs/venues` if that is unset. No unit on the Pi set the
variable, and the fallback dir did not exist, so no venue could be
armed. This failed safe: without a venue the gate cannot open. But it
blocked the DJ path completely.

While planning the fix, worker-1 found a second problem (plan
`67cce1d1`, Q1). The GM had a built-in first-boot default: it armed
`PI4AUDIO_DEFAULT_VENUE` if set, otherwise the hard-coded
`foh-passthrough`, and persisted that name. That default could not
fire only because the dir was missing. Packaging the venues alone
would have made it live, and `foh-passthrough` has no driver
protection (D-031).

### Fix (architect `827c2d69` §3, `bd68d14a`, `4c7eceaa`; audio-engineer `013d2fa8`, `16ab21eb`)

- The venues are packaged into the Nix store as a read-only
  derivation from the flake source (`flake.nix`, `venues`).
- `PI4AUDIO_VENUES_DIR` points at that store path for both the GM
  (`nix/nixos/services/graph-manager.nix`) and the web UI
  (`nix/nixos/services/web-ui.nix`), so both read one dir.
- `nix/checks/board-guard.nix` asserts that the GM unit carries the
  variable, that the dir exists and is not empty, and that the
  packaged venue file equals the flake-source file.
- No built-in default venue (Q1 = A, commit `90bb72de`). The GM arms a
  default only if `PI4AUDIO_DEFAULT_VENUE` is set, and no unit sets
  it. Audio-engineer (`16ab21eb`), verbatim: "a venue is armed only by
  an explicit set_venue, or by restoring the venue a previous explicit
  set_venue persisted; never by a built-in or env default unless the
  AE later opts in."
- F-467: the GM no longer reports a venue as active when its profile
  fails to load (commit `afaba039`).
- Docs in the same PR (commit `1eb84dac`): the `foh-passthrough.yml`
  header, US-113, D-062, US-127, a dated note in F-037, and a status
  line.

### Still open (close-out)

1. Deploy to the Pi 5 (parked: no Pi access while the owner is
   travelling). The first step of the deploy plan is binding
   (audio-engineer `16ab21eb`, amended by `c238cf12` after AD #74 M1:
   the GM falls back to `last-venue.bak` when `last-venue` is missing,
   unreadable or empty). It is a read-only OBSERVE step on the state
   dir the GM unit uses on the target generation (`PI4AUDIO_STATE_DIR`
   if the unit sets it, else `/var/lib/pi4audio`; both dirs if they
   differ between the running and the target generation): `ls -la
   <state dir>/`, and `cat` each of `last-venue`, `last-venue.bak` and
   `last-venue.tmp` that is present. Decision rule (`c238cf12` B3),
   verbatim: "STOP and report to the AE before the reboot into the
   F-465 generation if last-venue OR last-venue.bak EXISTS, in any
   state (empty, whitespace-only and unreadable all count). PROCEED
   only if both are absent. last-venue.tmp alone does not STOP, but its
   presence and content go in the report." The STOP report gives each
   file's `ls` line and `cat` output, and whether the named venue
   exists in `PI4AUDIO_VENUES_DIR` on the target generation. The AE
   then rules case by case. No one deletes or renames these files
   without that ruling.
2. On-device AC3 (b, c, d, e) on the new generation, not 3e alone
   (`013d2fa8` (B)2). AC3e reads `get_venue`, the GM journal "loaded
   ... gate closed" line, the YAML sha pin `3e9c7758` at the
   `PI4AUDIO_VENUES_DIR` path, and the pending gains. The AE-Q2
   handover sentence "venue armed: ..." is given then. AC3(e) also
   repeats the item 1 read after the reboot (`c238cf12` B4). PASS needs
   the files on disk to match `get_venue` and the journal: both files
   absent means no venue and the "no persisted venue ... starting with
   no venue" line. Files accepted under B3 mean the restored venue, gate
   closed, gains pending, and no "loaded venue ... from backup" warning
   unless the AE accepted a `.bak`-only restore. Any difference is a
   FAIL to the AE.
3. GM journal baselines that mark the old startup line as "known:
   F-465" are updated to the new line: "US-113: no persisted venue and
   PI4AUDIO_DEFAULT_VENUE unset — starting with no venue".
4. Whoever drops the F-465 rule from `safety.md` must, in the same
   batch, add a gate-open precondition for F-341 (audio-engineer
   `c54ab9f2`): today F-341 is covered before gate open only because
   the F-465 rule blocks every gate open.

F-465 closes when items 1-4 are done and the audio-engineer accepts
AC3 on the device.
