## F-400: PipeWire conf.d fragments deployed under store-hash names

**Severity:** medium (Architect, 2026-10-26)
**Status:** fixed on `story/US-173-first-dj-session` (`ff4d6c7e`, self-test `9b1aa8a1`), needs Pi evidence (US-173 P-step 15)
**Found in:** `nix/nixos/audio/pipewire.nix` (the `cp` lines for the conf.d fragments)
**Affects:** PipeWire and JACK conf.d load order and same-name user overrides: `10-audio-settings.conf`, `21-usbstreamer-playback.conf`, `30-filter-chain-convolver.conf`, `80-jack-no-autoconnect.conf`
**Related:** F-358 (05-rt-direct.conf, already copied under its plain name), F-318, US-173
**Found by:** worker-1 (F-358 review, option (A)) and quality-engineer (#63 nit, JACK fragment sort order); raised to a defect by the architect (2026-10-26)

### Description

`pipewire.nix` installed four conf.d fragments with `cp <store path>
dir/`, which keeps the store hash in the file name
(`<hash>-30-filter-chain-convolver.conf`). conf.d fragments load in file
name order, so the order was set by the store hashes, not by the `NN-`
prefixes. A user fragment overrides a deployed one only under the same
name, so same-name overrides did not work either. It was harmless so
far, but the order was accidental. `wireplumber.nix` already named its
destinations.

### Severity ruling (architect, 2026-10-26)

Medium, not P1:
- No wrong runtime value has been seen, and none is possible today. The
  four pipewire.conf.d fragments set disjoint sections (`module.rt.args`,
  `context.properties`, `context.objects`, `context.modules`), so the
  hash order changes no value.
- The defect is latent. A same-name user override would silently not
  replace the deployed fragment, and a future fragment that depends on
  the number order would load out of order. `checks.conf-fragment-names`
  in CI now guards both.
- It is not a safety issue. The D-063 gains and gate live in
  `30-filter-chain-convolver.conf`, which was unaffected.

### Fix

- The four `cp` lines in `pipewire.nix` name their destination files.
- New check `nix build -L .#checks.aarch64-linux.conf-fragment-names`
  (`nix/checks/conf-fragment-names.nix`, run in the CI test-and-build
  job). It reads the trees the `mugge-pi5-deploy` configuration deploys
  (`/etc/pipewire` and WirePlumber's config tree) and fails the build if:
  - 0. its own pattern does not reject a store-hash name and accept a
    plain one (self-test);
  - 1. any file in a `*.conf.d` directory does not match
    `^[0-9]{2}-[a-z0-9-]+\.conf$`;
  - 2. a fragment we deploy is missing under its plain name.

### Acceptance criteria

1. CI is green for `conf-fragment-names` and `jack-self-connect` at the
   final head (QE C1).
2. P-step 15 on the Pi lists the deployed conf.d names, and the user
   conf.d dirs under `~ela/.config` (expected empty; QE C2, AE).
3. The fix changes the load order, so the standard post-deploy checks
   run first, including the `pw-metadata` clock/quantum values and the
   USBStreamer node props being unchanged (QE C3, AE).
