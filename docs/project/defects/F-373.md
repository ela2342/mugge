## F-373: USBStreamer sink does not recover after USB re-enumeration

**Severity:** high for availability (audio-engineer); safety-relevant
**Status:** open. Not a US-163 blocker (AC17-B step (a) PASSED on safety; step (b) deferred here). AMPS-ON PRECONDITION LIST (Pi 5), items 8 and 13
**Found in:** US-163 AC17-B step (a), CM-CHG-.89-5 (2026-10-25), `mugge-pi5-deploy`; the static USBStreamer sink adapter in `pipewire.conf.d`
**Affects:** USBStreamer playback (all 8 channels), the PA at a gig, metering after recovery (F2)
**Related:** US-159 (G16), US-163 (AC17, AC16b), D-063, F-361
**Found by:** worker-1 (AC17-B step (a)); rated by audio-engineer (2026-10-25)

### Description

After the authorized USB re-enumeration (authorized 0 -> 1), the
USBStreamer sink node (id 33) stays "running" on a dead PCM. From
13:46:33Z PipeWire logs spa.alsa "hw:USBStreamer,0p: No such device"
continuously; after authorized = 1 at 13:46:38Z it never reopens the
device. The hardware Playback Channel Map reads all 0, so no PCM is
open.

Likely cause (audio-engineer): the sink is a static `pipewire.conf.d`
adapter with no hotplug path, so only a PipeWire restart recovers it.

Raw evidence:
`~/mugge-pi5-prewipe-20261024/ac17-B-replug-a-20261025T134631Z.txt`
(sha256 455610c2...). AC17-B step (b), the owner's physical replug,
is deferred to this record (AE, QE ruling; PO, 2026-10-25); it is not a
US-163 AC.

Impact (audio-engineer):
- Availability: after any USB glitch at a gig the PA goes silent. The
  only fix is a PipeWire restart, which also kills the meters (F2).
- Safety: if the node ever recovers on its own, programme audio
  resumes abruptly at full gain, not at Mult 0.

Current interim recovery procedure (audio-engineer, verified in
AC17-B step (c), raw sha256 5aad9083... and 64fdbcdf...): a PipeWire
restart plus a bridge restart recovers the sink. This is today's
manual workaround, not the fix. Graph-manager's watchdog re-armed,
the 16 gains came up at exactly 0, the gate stayed closed (D-063
fail-safe), and the PCM reopened with its channel map restored.

### Acceptance criteria

1. The required behaviour is defined under US-159 G16: either every
   recovery goes through the D-063 gate (gains 0, then a deliberate
   ramp), or there is no self-recovery and only an operator-initiated
   restart (audio-engineer).
2. The fix is re-tested on the Pi 5 with a USB re-enumeration and a
   physical replug, using the AE's AC17-B step (b) read set, before
   and after: the node list (any new nodes), the USB devnum, the
   kernel log, spa.alsa errors, the gains, the gate state and the hw
   mixer controls (amps off, HP/IEM disconnected and their amps off,
   owner warned first). The result matches AC1; raw output recorded.
3. Resolved before any amps, HP or IEM use of the Pi 5 (AMPS-ON
   item 8: "F-373 fixed and re-tested with a physical replug").
4. Re-open trigger (AE, PO): if the USBStreamer hw volume is ever set
   below 0 dB (e.g. by US-159), OR the WP rule / link management for
   the USBStreamer changes (disable rule, autoconnect, GraphManager
   re-adoption), the physical replug is a required safety test again.
5. Safety shape (audio-engineer, verbatim): "After a USBStreamer
   re-enumeration (software and physical replug), the sink recovers
   by whatever route the fix chooses. At the moment audio can flow
   again, all 16 gains are exactly 0 and the gate is closed (D-063);
   levels return only through a deliberate gate open/ramp. Meters
   recover (F2). There is never an abrupt resume at the previous
   gain."
