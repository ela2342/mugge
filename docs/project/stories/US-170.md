## US-170: Pi 4 config hardening parity

**As** the owner keeping the Pi 4 configuration as the US-164 baseline,
**I want** the Pi 4 `mugge` config to get the same network allowlist and configuration revision as the Pi 5,
**so that** the Pi 4 image is never weaker than the Pi 5 one if it is ever used again.

**Status:** draft (PO, 2026-10-24, from worker-1)
**Priority:** blocks any amps-on Pi 4 use (security)
**Depends on:** US-163
**Related:** US-163 (AC1a pi4-noop stays as written: this story deliberately changes the Pi 4 drvPath; T55 re-scoped here), US-000a, F-037, F-358, D-069

### Acceptance criteria

- [ ] AC1: The Pi 4 config gets the same 8080/5900 ip saddr allowlist as the Pi 5: fails closed when empty, IPv6 covered.
- [ ] AC2: `system.configurationRevision` is set, and `nixos-version --configuration-revision` reports it.
- [ ] AC3: The Pi 4 toplevel builds; the nft ruleset is verified with eval/build checks (no Pi 4 hardware is available).
- [ ] AC4: Any drvPath pin added for US-163 AC1a is removed here at the latest.
- [ ] AC5 (T55, re-scoped from US-163; PO, architect concurs): the full Pi 4 builds of `mugge` and `images.sd-card` at the branch SHA, store paths recorded. The US-163 PR states that the Pi 4 runtime change (`05-rt-direct.conf`, F-358) is unverified on hardware.
- [ ] AC6 (F-358 on the Pi 4; AE, QE): before any Pi 4 amps-on or audio use, US-163 AC13 A1 passes on the Pi 4: every data-loop thread of the single pipewire PID at FF/88 after a cold boot and after one announced PW restart, no RTKit lines, RTTIME 200000/200000, plus "NRestarts 0, no SIGKILL at startup with production 16k-tap coefficients" (AD L1). Until then F-358 stays open as "Pi 4 verification outstanding".
- [ ] AC7: The Pi 4 gets a WirePlumber ALSA card-block rule like the Pi 5's `54-disable-other-alsa-cards` (Pi 5 only today; pre-existing gap; AE).
