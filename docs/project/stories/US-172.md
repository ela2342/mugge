### Background

US-163 found that the Pi 5 firmware merges none of the `config.txt`
`dtoverlay` lines (`vc4-kms-v3d-pi5`, `disable-bt-pi5`). The
bootloader writes them correctly and the firmware looks in the right
directory (`os_prefix` and `overlay_prefix` point at
`gens/<id>/overlays/`, which holds the README and both dtbo files),
but nothing is applied. Every GPU/HDMI DT node stays
`status=disabled`, so vc4/v3d never autoload, there is no
`/dev/dri`, and greetd crash-looped until US-163 guarded it
(`f87c162b`, F-367). Bluetooth also stays active (BT still on
`serial@7d50c000`).

Starting point (architect): read `/proc/device-tree/chosen/log` (the
firmware log) for overlay load or apply errors. Firmware 2025-08-28,
variant `start_cd`. Candidate causes: Pi 5 firmware handling of
`os_prefix` overlays; the dtbo files coming from the
bcm2711_defconfig RT kernel build. Evidence:
`~/mugge-pi5-prewipe-20261024/diag-F367-overlay*-798f2dc7.txt`.
Superseded by the starter set below (CM-OBS-.89-DRM1).

### Starter set (architect, PO, CM; 2026-10-25, from CM-OBS-.89-DRM1)

- Diagnosis (architect; evidence drm-observe `4d7b6864`, s5
  `9868a2fc`, s1011 `3fd2c3c3`): the firmware applies ZERO overlays
  with our `config.txt`. `disable-bt-pi5` is not applied (the BT
  node has no status); every display node stays at the base-DTB
  "disabled". Our artefacts are fine: offline `fdtoverlay` applies
  the KMS overlay cleanly. So it is our bug in the `bootloader.nix`
  `config.txt` layout. Lead cause, NOT yet proven: every
  `dtoverlay`/`dtparam` line comes before `os_prefix=gens/<id>/`,
  and nothing is at the FAT root.
- First fix candidate: in `configTxt` emit `os_prefix=` (with
  kernel/initramfs/cmdline) before the dt lines, about 5 lines
  reordered. Also switch greetd off explicitly until it is ordered
  after DRM (architect addendum); then greetd ordered after DRM
  (AC8, PO).
- Test plan (architect, CM, 2026-10-25; replaces both the 4-step
  hand-edit of `config.txt` on the FAT and the interim "deploy as a
  new generation" step 1). Both steps come after US-163 AC19.
  - Step 1 = one TRYBOOT of the CURRENT generation (CHANGE; worker-2
    implements it with pinned scripts). `tryboot.txt` holds the
    reordered `config.txt`; `config.txt` is never written. The tar
    backup of the FAT is deleted after a `cmp` (CM wording; the
    pinned scripts are authoritative). Sequence: pre reads; announced
    `reboot '0 tryboot'`; TRYBOOT reads (the BT status,
    `axi/v3d@2000000` status, `/dev/dri`, `lsmod` vc4/v3d); restore;
    an announced normal reboot; RESTORED reads. A power cycle
    recovers. PASS = BT disabled + v3d okay (order theory confirmed);
    no change = order theory wrong.
  - Step 2, only after a step 1 PASS = deploy the branch (DEPLOY) as
    a new generation (`nixos-rebuild boot`, not `switch`), pre reads,
    announced reboot, post reads. Rollback per
    `docs/guide/howto/nixos-upgrade.md` §8.5 (previous generation).
  - Each reboot announcement names the recovery route (power cycle
    for step 1, the §8.5 rollback for step 2; card reader/owner as
    fallback) (PO).
- Fallback if no change: the firmware log via vclog. Its `/dev/mem`
  read is CHANGE with its own CM go, not OBSERVE (CM, 2026-10-25).
- The F-367 guard stays in place until the fix is confirmed (PO).
- Timing: after #50 merges and US-163 AC19 (focus); the CM
  schedules the session.
