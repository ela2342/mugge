### Background

US-163 found that the Pi 5 firmware merges none of the `config.txt`
`dtoverlay` lines (`vc4-kms-v3d-pi5`, `disable-bt-pi5`). The
bootloader writes them correctly and the firmware looks in the right
directory (`os_prefix` and `overlay_prefix` point at
`gens/<id>/overlays/`, which holds the README and both dtbo files),
but nothing is applied. Every GPU/HDMI DT node stays
`status=disabled`, so vc4/v3d never autoload, there is no
`/dev/dri`, and greetd crash-looped until US-163 guarded it
(`f87c162b`, F-367). Bluetooth also stays active (BT still on
`serial@7d50c000`).

Starting point (architect): read `/proc/device-tree/chosen/log` (the
firmware log) for overlay load or apply errors. Firmware 2025-08-28,
variant `start_cd`. Candidate causes: Pi 5 firmware handling of
`os_prefix` overlays; the dtbo files coming from the
bcm2711_defconfig RT kernel build. Evidence:
`~/mugge-pi5-prewipe-20261024/diag-F367-overlay*-798f2dc7.txt`.
Superseded by the starter set (CM-OBS-.89-DRM1), and that in turn
by the route below.

### Route so far (2026-10-25 to 2026-10-31)

All test boots are one-shot tryboots: a reset falls back to the
normal boot. Unless noted, every run used our RT kernel built from
`bcm2711_defconfig` (the Pi 4 config, 4K pages).

- Starter set (2026-10-25, architect, PO, CM, from CM-OBS-.89-DRM1):
  the firmware applied no overlays, and the lead theory was the
  `config.txt` line order. Run 1 put `os_prefix=` before the
  `dtoverlay` lines and still applied nothing, so the order theory is
  refuted (architect, 2026-10-31).
- Runs 2-4 (2026-10-25/26, overlays applied through
  `overlay_prefix=o/`): runs 2 and 3 hung (power pull); run 4 came
  back by itself after a kernel panic and reset.
- Run 5 (2026-10-27), one change per tryboot, each classified by the
  architect:
  - R5a (no overlay applies, marker cmdline only) = TRYBOOT. The
    tryboot mechanism works on this Pi 5 and EEPROM.
  - R5b (both overlays through `o/`, plus
    `modprobe.blacklist=vc4,v3d softlockup_panic=1 hung_task_panic=1`)
    = FAIL-K: an early kernel panic, then the `panic=60` reset. The
    panic text was never captured.
  - R5c (only `vc4-kms-v3d-pi5`) = FAIL-K. R5d (only `disable-bt-pi5`)
    = FAIL-K.
  - Every return state was safe (gains 0, gate closed, no `/dev/dri`).
- What runs 1-5 settle (architect, 2026-10-31): the added cmdline
  options are not the cause (runs 2 and 3 failed without them), and
  either overlay alone triggers the failure. The kernel dies within
  about 10 seconds whenever the firmware applies one of our overlays.
- Known-good comparison K1-K4 (`a3212f67`, against the Raspbian
  install that had graphics on this Pi): the firmware and EEPROM are
  the same. Two real differences remain: (a) the kernel (our
  `bcm2711_defconfig` RT build vs Raspbian's `bcm2712_defconfig`,
  16K pages) and (b) where the overlays sit (deep under `gens/<id>/`,
  or via `o/`, vs a short `overlays/` at the FAT root).
- Architect r2 (`bb45927f`, 2026-10-27; triggered by the owner: "The
  kernel has been built with a Pi 4 configuration and this isn't the
  first thing you check?"): test the kernel config. R6a steps (i)-(iii)
  are done: the board option `mugge.board.kernel.defconfig` and the
  `kernel-rt.nix` change (`250199bc`, Pi 4 unchanged), the toplevel
  build (2 h 07 min) and the `.config` check (`ARM64_16K_PAGES=y`,
  `PREEMPT_RT=y`, `DRM_VC4=m`, `DRM_V3D=m`; report `583a7827`). The
  build outputs have since gone from the Mac store, and they were
  never copied to the Pi (state capture `f60aa960`), so the kernel
  has to be rebuilt.
- Current plan (architect restart reading `ee7e28f4`, 2026-10-31).
  Two hypotheses, tested in parallel:
  - H-o (lead): the firmware's handling of overlays under `os_prefix`
    plus `overlay_prefix=o/` gives a device tree the kernel can't
    boot. Without `o/` the overlay paths are 66-67 characters long,
    which fits a ~64-byte firmware path limit (inference, not proven)
    and would explain why the normal boot applies no overlays.
  - H-k (close second): our kernel (Pi 4 config and/or RT) panics on
    any firmware-modified device tree.
  - R5s, no build: one tryboot of the current generation with its
    files copied to a short FAT directory `t/` (longest overlay path
    31 characters) and no `overlay_prefix`. TRYBOOT confirms H-o
    (fix: a short per-generation FAT directory in `bootloader.nix`);
    FAIL-K rules H-o out.
  - Kernel rebuild (route C): a GitHub Actions `ubuntu-24.04-arm` job
    on the experiment branch builds the toplevel into the `mugge`
    cachix; the Pi fetches it from cachix under CHANGE. Nothing is
    built on the Mac (2026-10-31: about 2 GiB free, stop line
    10 GiB). Fallback (route P): build on the Pi itself, under CHANGE
    with its own thermal rule.
  - R6a': the R5s layout with the bcm2712 RT kernel, after R5s is
    classified and the build is on the Pi. One variable against R5s.
  - If R6a' also fails: a device tree pre-merged on the Pi (no
    firmware overlay step), or capturing the panic text via a UART
    adapter (owner task, F-441). Each is ruled when reached.
  - The architect classifies every outcome; the CM sequences the
    steps.
- Pi 5 state on 2026-10-31 (`f60aa960`, OBSERVE): booted generation 6
  (`a11skqm2`), the bcm2711-config RT kernel (4K pages); every GPU and
  display node is `disabled`, no `/dev/dri`, greetd skipped by the
  F-367 guard.
- Unchanged from the starter set: the F-367 guard stays in place until
  the fix is confirmed (PO). Each reboot announcement names the
  recovery route (PO). While nothing is connected to any output,
  reboots need an announcement only.
